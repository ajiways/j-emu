# Правила разработки j-emu

## Никаких неявных fallback и значений по умолчанию

Если обязательного значения, конфигурации, каталожной записи, связи или обработчика
нет, выполнение должно завершиться явной диагностируемой ошибкой.

Запрещено:

- подставлять «безопасные», нулевые, пустые или исторические значения;
- заменять отсутствующего моба, предмет, локацию или пользователя другой записью;
- возвращать успешный пустой wire-ответ для неподдержанной операции;
- скрывать ошибки чтения, декодирования, импорта или сохранения;
- использовать `??` / `||` для маскировки отсутствующих обязательных данных;
- иметь defaults у обязательных env-переменных и бизнес-полей;
- продолжать частичную транзакцию после ошибки.

Разрешены только явно названные и валидируемые бизнес-правила, например
`HeroCreationPolicy` или `FightRules`. Это не fallback: policy обязательна,
версионируется и передаётся вызывающей стороной.

На wire:

- неизвестная или запрещённая операция возвращает документированный `status:203`
  с полем `error`;
- отсутствие сессии возвращает `status:4`;
- внутренняя ошибка возвращает `status:204`, логируется с correlation id и не
  превращается в пустой `status:100`.

Тесты обязаны покрывать fail-fast поведение для отсутствующих зависимостей и
данных.

## Архитектурные границы

- Playerbots в этом репозитории нет. В будущем это отдельный сервис.
- Модули обращаются друг к другу только через публичные application ports.
- Framework-код не импортируется в domain/application.
- Stateful domain/application компоненты оформляются классами; чистые codecs,
  mappers и детерминированные вычисления остаются функциями.
- Тесты находятся только в `tests/` и используют constructor injection,
  builders, fakes и явные fixtures.

## Persistence и идентификаторы

- Runtime использует PostgreSQL через Drizzle ORM. `postgres.js` является
  драйвером, а не API репозиториев.
- Raw SQL допустим только для возможностей PostgreSQL, которых нет в Drizzle,
  с объяснением причины рядом с запросом и отдельным integration/e2e тестом.
- Drizzle-схемы принадлежат модулям. Чужие таблицы нельзя изменять напрямую;
  внутри общего PostgreSQL разрешены FK и одна транзакция orchestration-сценария.
- Production in-memory repositories для персистентных данных запрещены.
  Test fakes находятся только в `tests/support`.
- Активный бой — исключение: его hot state живёт только в process memory.
  PostgreSQL не хранит active fights, participants, turns, effects, packets,
  checkpoints или event log.
- После завершения боя сохраняется только совместимая со старым
  `finished_fights` history row. Retention — 72 часа; cleanup выполняется
  отдельными batches вне finish/read request path. Источник контракта и
  допустимая нормализация: ADR-0015.
- Все runtime ID выдаёт PostgreSQL через identity/sequence/default. Запрещены
  process counters, `max + 1`, ручное смещение ID и генерация persisted ID в
  domain/application.
- Канон ID: `jgr-emu/docs/ID_RANGES.md`, ADR-0016 и
  `docs/architecture/ID_POLICY.md`. Не копировать исторические floors из старого
  кода.
- Persistent identity начинается с `1`. Исключение: `items.id` экземпляра
  предмета начинается с `100_000` из-за коллизии `persSpells.srcId`.
- `artikul_id` каталога сохраняется из контента и не принадлежит sequence
  `items.id`.
- Human participant боя равен numeric `heroes.id`; fight bot ID ephemeral,
  выдаётся в RAM от `1_000_000` и не сохраняется.
- Wire integer находится в `1..2_147_483_647`. Ноль запрещён, кроме
  `answer_id=0` (доска) и `instance_id=0` (мир).
- Map hunt ID = `area × 100 + index`; dungeon hunt уникален в том же
  `common|hunt`. BG/dungeon copies различаются типом, не диапазоном.
- Миграции генерируются Drizzle Kit с осмысленным именем
  `--name=<module>_<change>`. Применённые миграции не редактируются.

## Контент

- `jgr-emu`, `_research`, dumps и fixtures — только read-only evidence/import
  corpus. Код старого runtime не переносится.
- Editor и importer работают с versioned drafts в PostgreSQL. Publish создаёт
  immutable release и атомарно активирует runtime projection.
- SQLite, файловый dual-write и runtime-чтение fixtures запрещены.
- Некорректная запись отменяет candidate release целиком; строки не
  пропускаются и не исправляются автоматически.

## Wire и команды клиента

- `AmfValue` разрешён только внутри codec/framing и низкоуровневого decoder.
  Handlers, application и domain используют точные DTO.
- Fastify route остаётся тонким: decode → static registry → typed handler →
  response mapper.
- Dynamic imports (`import()` и `await import`) запрещены. Все handlers
  регистрируются статически в composition root/module factory.
- Один основной exported class/interface на файл. Семейство DTO можно держать
  вместе только для одного небольшого контракта.
- Handwritten production-файл пересматривается при 250 строках и не может
  превышать 400 строк. Исключения: generated codec и миграции.

## Тестирование

- Приоритет — e2e через реальные Fastify routes, raw AMF и отдельный PostgreSQL
  с суффиксом `_test`.
- Unit-тесты оставляются для codec/framing, детерминированных формул и сложных
  state machines. Integration-тесты — для Drizzle transaction/locking,
  миграций и публикации контента.
- E2e не использует memory persistence и обязан проверять reconnect/restart там,
  где состояние должно переживать процесс.

## Поиск по коду и индекс

- Для структурного поиска сначала используется MCP `user-codebase-memory-mcp`.
- В начале работы проверить `list_projects` и `index_status`. Если проекта нет в
  индексе, выполнить `index_repository` с `mode:"full"` и `persistence:true`.
- Ориентация: `get_architecture`; поиск символов: `search_graph` с пагинацией;
  исходник: `get_code_snippet`; callers/callees: `trace_path`.
- Перед отрицательным или исчерпывающим выводом проверить
  `check_index_coverage`. Непокрытые ranges проверить через `rg`/чтение файлов.
- `search_code`/`rg` используются для текста, конфигурации, fixtures и когда
  graph coverage недостаточен, а не как первый способ структурного поиска.
- После существенных правок выполнить `detect_changes`, затем обновить индекс
  изменённого проекта через `index_repository` с `mode:"full"` и
  `persistence:true`. Нельзя передавать работу с заведомо устаревшим индексом.

## Git workflow

- Агент сам решает, нужен ли feature branch и когда фиксировать локальный
  commit. Дополнительное подтверждение пользователя для безопасных локальных
  branch/commit операций не требуется.
- Отдельный branch создаётся для существенного или изолированного изменения,
  особенно если текущая ветка общая/защищённая либо работа делится на несколько
  reviewable этапов.
- Commit создаётся после завершения когезионного изменения и прохождения
  относящихся к нему проверок. Сообщение описывает результат, а не процесс.
- Нельзя включать в commit чужие или несвязанные изменения. Перед commit
  проверить status и diff.
- Запрещено переписывать историю, выполнять destructive reset/checkout или
  удалять чужие ветки без явного запроса.
- Push и PR выполняются самостоятельно только когда задача явно включает
  внешнюю публикацию/передачу результата; наличие remote само по себе не является
  разрешением на push.

## Quality gates

- Форматирование выполняет Prettier, статическую проверку — ESLint.
- `npm run dead-code` через Knip обязан завершаться без unused files, exports,
  exported types, dependencies, unresolved imports, duplicate exports и cycles.
  Экспорт не считается используемым только потому, что он объявлен `export`.
- Runtime/tooling entry points обязаны быть видны Knip через `package.json`
  scripts и поддерживаемые config plugins; дополнительные entry points
  перечисляются в `knip.json`. Добавлять broad ignore/allowlist вместо удаления
  мёртвого кода запрещено; точечное исключение требует причины, владельца и срока
  удаления рядом с конфигурацией.
- Перед передачей изменения должны пройти `npm run format:check` и
  `npm run lint`, `npm run dead-code`; для production-кода также `npm run build`
  и релевантные тесты. Полный локальный gate — `npm run check`.
- Pre-commit hook через Husky/lint-staged форматирует и проверяет staged-файлы.
  После staged-проверок hook запускает Knip по всему проекту. Обход hook через
  `--no-verify` запрещён, кроме явно диагностированного сбоя tooling с
  зафиксированной причиной.

## Документация

- Документация обновляется в том же изменении, которое меняет архитектурное
  решение, публичный контракт, wire shape, конфигурацию, миграцию, команду
  запуска или эксплуатационную процедуру.
- Документ описывает текущую проверяемую истину. Планы и ещё не реализованное
  поведение явно помечаются как план; их нельзя выдавать за возможности runtime.
- Не создавать документ «для полноты». Новый файл нужен только когда у него есть
  конкретный читатель, вопрос и каноническая ответственность.
- Писать коротко и предметно: решение, ограничения, причина, пример команды и
  критерий проверки. Запрещены вводная вода, общие учебные объяснения,
  повторение очевидного кода и копирование одного текста в несколько файлов.
- Канонический факт хранится в одном месте; остальные документы ссылаются на
  него. При изменении решения обновить ссылки и удалить либо явно пометить
  устаревшее описание.
- ADR создаётся только для долгоживущего решения с реальными альтернативами и
  последствиями. Routine change, пересказ задачи и журнал действий не являются
  ADR.
- Команды, пути, env-переменные и примеры в документации проверяются перед
  передачей. Если проверить пример нельзя, это указывается явно.
- Изменение не считается готовым, если относящаяся к нему документация врёт,
  расходится с кодом или оставляет два противоречивых источника истины.
