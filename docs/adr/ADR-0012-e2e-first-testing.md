# ADR-0012: E2E-first стратегия тестирования

- Статус: Accepted
- Дата: 2026-09-07
- Заменяет: [ADR-0007](ADR-0007-testing-strategy.md)

## Контекст

Главный риск `j-emu` находится не внутри отдельных классов, а на сквозной границе:
старый клиент отправляет raw AMF в реальные Fastify routes, обработчики меняют
состояние PostgreSQL, а ответ должен сохранить точный wire shape. Тест сервиса с
fake-репозиторием не обнаруживает ошибку content-type parser, cookie, транзакции,
маршрута, AMF framing или несовпадение схемы БД.

ADR-0007 ставил небольшой E2E-набор после нескольких слоёв более узких тестов.
На текущем этапе это создаёт ложную экономию: один и тот же сценарий приходится
повторять в application, contract и E2E tests, но интеграционные разрывы всё равно
обнаруживаются поздно.

## Решение

При разработке пользовательского сценария первым пишется E2E-тест. Он:

1. поднимает настоящее приложение через production module factories;
2. вызывает реальные Fastify routes через `inject`;
3. передаёт raw AMF bytes и декодирует raw AMF/MULTI-ответ;
4. использует отдельную PostgreSQL test database с настоящими миграциями;
5. создаёт уникальные account/hero/content IDs и не зависит от общего состояния;
6. проверяет видимый клиенту результат и подтверждает персистентность повторным
   запросом либо перезапуском приложения, когда это существенно;
7. проверяет fail-fast и документированные `status:4/203/204`, а не только happy
   path.

E2E — основной тест поведения OA, fproxy и esrv. Запрещено заменять Fastify route
прямым вызовом handler/service, raw AMF — готовым DTO, а PostgreSQL — production
memory repository.

### Где остаются unit-тесты

Unit-тест допустим только для границы, которой полезна изоляция:

- AMF codecs и SINGLE/MULTI framing;
- детерминированные формулы;
- сложные state machines с детерминированными clock/RNG/ID;
- чистые parser/mapper primitives, если E2E плохо локализует байтовую ошибку.

Unit-тесты не дублируют простой CRUD, orchestration или handler branching.
Моки Fastify, Drizzle и application services не являются заменой E2E.

### Где остаются integration-тесты

Integration-тесты с реальным PostgreSQL выделяются только для:

- Drizzle-транзакций, commit/rollback и границ Unit of Work;
- конкурентных изменений, row/advisory locking и idempotency;
- накатывания миграций вперёд на чистую и уже мигрированную БД;
- импорта, валидации и атомарной публикации контента.

Обычные repository CRUD cases проверяются через E2E, если в них нет отдельного
SQL-инварианта.

## Изоляция PostgreSQL

`TEST_DATABASE_URL` обязателен и должен указывать на отдельную БД. Harness
отказывается работать с production/development URL и не имеет memory fallback.
До suite применяются все миграции. Каждый тест создаёт собственные данные;
очистка выполняется по известным ID или транзакционно и не использует существующих
пользователей. Параллельный запуск не должен приводить к конфликтам ID.

Сбой миграции, seed или cleanup завершает suite ошибкой. Skipped DB tests и
успешный пустой прогон не считаются проверкой.

## Практический цикл

1. Добавить один failing E2E для требуемого wire-сценария.
2. Реализовать минимальный вертикальный путь route → DTO → handler → Drizzle.
3. При сложной формуле/state machine вынести узкий unit-test.
4. При транзакционном или конкурентном риске добавить узкий integration-test.
5. Запустить E2E повторно, затем полный набор и build.

Регрессия получает тест на самом высоком уровне, который надёжно воспроизводит
дефект. Узкий тест добавляется только если он улучшает диагностику или фиксирует
сложный инвариант.

## Последствия

- Wire, transport и persistence проверяются одним исполняемым сценарием.
- E2E требуют PostgreSQL и стоят дороже, поэтому сценарии должны быть короткими,
  изолированными и без произвольных ожиданий.
- Unit/integration suite становится меньше и имеет явную специализацию.
- Текущий memory-based `ApplicationHarness` не соответствует решению и должен
  быть мигрирован до объявления E2E gate обязательным.

## Критерий соблюдения

Новый OA/fproxy/esrv command не принимается без raw-AMF E2E через Fastify и
PostgreSQL. Исключение требует отдельного ADR с причиной, владельцем и сроком
удаления.
