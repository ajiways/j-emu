# ADR-0010: Drizzle как стандарт persistence

- Статус: Superseded by [ADR-0018](ADR-0018-postgres-content-and-identifiers.md)
- Дата: 2026-09-07

## Контекст

Серверу нужен один понятный способ описывать таблицы, выполнять запросы и
управлять миграциями. Несколько ORM, ручные миграции и production-хранилища в
памяти создают разные модели данных и затрудняют проверку изменений.

## Решение

Для persistence обязательны Drizzle ORM и `drizzle-kit`.

- `postgres.js` используется только как нижележащий драйвер Drizzle.
- Обычный доступ к данным выполняется через Drizzle.
- Raw SQL допустим только как явно документированный escape hatch, когда
  Drizzle не может выразить нужную операцию или измерения показывают
  неприемлемый SQL/план. Рядом с таким кодом должны быть причина, ограничения и
  тест.
- Каждый модуль владеет своими файлами Drizzle schema и своими таблицами.
- Миграции генерируются через `drizzle-kit` с содержательным именем,
  переданным через `--name`.
- До объявления первого стабильного baseline цепочку `drizzle/` можно
  схлопнуть и перегенерировать snapshot/journal; существующие БД не
  сохраняются.
- После baseline сгенерированная и применённая миграция неизменяема.
  Исправление оформляется новой миграцией.
- Для постоянных данных production-репозитории в памяти запрещены. In-memory
  реализации допустимы только как test fake.

Используется один Postgres для всего модульного монолита. Модули сохраняют
владение таблицами и не записывают напрямую в чужие таблицы. Между
модульными таблицами разрешены внешние ключи, а одна бизнес-операция может
изменять данные нескольких модулей в одной транзакции. Такие изменения
координируются через публичные application ports владельцев.

Это решение уточняет ADR-0002 и ADR-0003 и заменяет запрет межмодульных FK и
общей транзакции из текущей архитектурной документации. Запрет прямой записи
в чужие таблицы сохраняется.

## Последствия

- Schema и миграции проверяются единым набором инструментов.
- Postgres остаётся общей точкой атомарности без размывания владения данными.
- Интеграционные тесты нужны для FK, транзакций и миграций.
- Выделение модуля в отдельную БД потребует разрыва его FK и транзакционных
  связей.

## Пересмотреть, когда

- модулю действительно требуется отдельная БД или независимый deployment;
- Drizzle не поддерживает обязательную возможность Postgres;
- измеренная нагрузка требует другого persistence-подхода.
