# ADR-0013: Идентификаторы постоянных сущностей генерирует БД

- Статус: Superseded by [ADR-0016](ADR-0016-live-derived-id-allocation.md)
- Дата: 2026-09-07

## Контекст

Исторический код использовал process-local счётчики, `max(id) + 1`,
арифметическое преобразование ID и ID, созданные приложением. Эти способы
дают коллизии при параллельной работе и после перезапуска.

## Решение

Идентификатор новой постоянной сущности генерирует Postgres через identity,
sequence или подходящий default. Drizzle получает созданную запись и её ID
через `returning`.

Криптографические session secrets, correlation IDs и idempotency keys не
являются ID persisted aggregate и могут создаваться application/edge-слоем.

Для постоянных сущностей запрещены:

- process-local счётчики;
- `max(id) + 1`;
- арифметическое преобразование одного ID в другой;
- генерация UUID в приложении.

Если подтверждённый wire-контракт требует числовой диапазон, используется
отдельная ограниченная нециклическая sequence Postgres. Её namespace, границы,
владелец и назначение должны быть явно описаны. Пересечение диапазонов допустимо
только при доказанной изоляции client namespaces. Исчерпание диапазона является
ошибкой, а не поводом перейти к другому диапазону или начать цикл.

ID authored content сохраняются при импорте без перенумерации. Они назначаются
автором контента и не являются runtime-ID новых постоянных сущностей.

Канонический реестр namespace, статусов, границ и источников находится в
[`ID_POLICY.md`](../architecture/ID_POLICY.md). На момент принятия ADR для
реализации назначен только `inventory.item_instance`. Старые floors/formulas
point, fight и participant остаются evidence со статусом `unassigned`.

Формулы, константные ID и локальные счётчики использовать нельзя. Диапазон,
который не подтверждён контрактом или дампами, нельзя угадывать или занимать
«на будущее».

Это решение заменяет требование выдавать UUID владельцем агрегата из текущей
документации модели данных для новых постоянных сущностей.

## Последствия

- Параллельные workers и рестарты не создают коллизии ID.
- Создание сущности требует обращения к БД до публикации её ID.
- Старые арифметические схемы нужно заменять sequence с проверенными границами.
- Импорт authored content обязан проверять уникальность сохранённых ID.

## Пересмотреть, когда

- подтверждённый wire-контракт требует другой схемы ID;
- сущности создаются независимо в нескольких БД;
- Postgres перестаёт быть источником постоянного состояния.
